# R11M runtime report: usable OS stretch (directories, virtual consoles, job control, VFAT)

Branch `r11m-os-usability`, from the frozen R11L `81d29ea900b60955837cbb394ea6176e9ffa9fa1`. The frozen rounds below it (R11H-FIX1 `4affc37`, R11I `bc9a90f`, R11J `f7664d7`,
R11K `82405025…`, R11L) are unchanged. The exact source commit of this package is in `PACKAGE.md`; numbers below are in `logs/r11m/SUMMARY.txt` (generated by
`scripts/r11m-summary.py`) and are repeated here only where a claim needs them.

## 0. Verification policy and status (read first)

After seven hours the verification requirements were changed explicitly: **QEMU VGA is the primary integration and regression environment.** The CPU-only i386VM block harness and the
interpretive Tiny386 *headless* runner are legacy diagnostic targets, not release gates; results already obtained on them are kept and labelled with the exact configuration. The windowed
full-machine Tiny386 build was **not tested**. The Tiny386-headless matrix was stopped in its third round; rounds 1 and 2 are complete and counted, round 3 (only `fs`, `con`, `conin` ran) is **not counted**.
Nothing was re-run to fill a quota. **No crash-safe-write claim is made**; one open storage finding (two FAT copies differing after a killed Tiny386 run) is recorded in
`docs/R11M-KNOWN-LIMITATIONS.md` section 5 and deferred to a storage-hardening milestone.

## 1. What the milestone delivers

The question for R11M was "can a person sit at this system and use it", not "how many tests print". At a QEMU VGA screen, with the R11M shell:

| Facility | What you can do | Where it is specified |
|---|---|---|
| Directories | `PWD`, `DIR [path]`, `MD`, `RD`, `CD`, relative and absolute paths, `..`, `COPY`, `REN`, `DEL`, `TYPE`, `RUN path`; the prompt shows the directory; every program sees the same paths through the C library | `docs/R11M-FAT-PATH-ABI.md` |
| Virtual consoles | four 80x25 text consoles; Alt+F1..F4 select; each has its own screen, cursor, attributes, input queue; cooked line editing; a program can write to its console while another has the focus | `docs/R11M-CONSOLE-ABI.md` |
| Job control | `START prog [args] /CON:n`, `PS`, `WAIT id`, `KILL id`; two copies of programs linked at the same origin run together on different consoles (paged image windows, R11K); the shell comes back after a kill and everything the job held is reclaimed | `docs/R11M-JOB-CONTROL-ABI.md` |
| Long file names | `COPY LONG.TXT "My Report 2026.txt"`, `MD "My Documents"`, `WIN1:/SRC/SUPERBASIC_INTERPRETER.C`; the 8.3 alias (`SUPERB~1.C`) works too; `DIR` shows both; host tools (mtools, `fsck.fat`) agree | `docs/R11M-VFAT-LIMITATIONS.md` |

None of this changes the CPU core, the boot path, the R11K paging launch path, the R11I host-backed block device or the R11L writable FAT16 layer. The six frozen default
images are byte-identical to R11L (`scripts/r11l-default-check.sh`, re-run on the final tree). It is **not** memory protection: all programs share ring 0
and the heap/stack area (`docs/R11M-KNOWN-LIMITATIONS.md`).

## 2. Method

* Guest programs and the shell are cross-built on the host with the historical GCC 1.40 (strict C89 for new common/runtime code), linked into slot-1 a.out images and run
  **inside the guest**. Kernel code is built for six configurations (i386VM plain/paging, Tiny386 plain/paging, QEMU VGA plain/paging).
* Writable tests run only on disposable copies of a deterministic scratch volume (`scripts/r11m-demovol.sh`); the initial volume's hash is checked after the run; the
  frozen R11K/R11H volumes' hashes are checked before/after the regression (UNCHANGED).
* Every run has a bounded timeout and explicit completion markers (a prompt, `exit status`, a banner). The QEMU driver (`scripts/r11m-qemu-capture.py`) types through the
  monitor (`sendkey`) and samples the VGA text buffer (`xp /4000xb 0xb8000`); the Tiny386 driver types through its terminal; the i386VM harness feeds a byte stream.
* Judges that do not trust the guest: `fsck.fat` 4.2, mtools (`mdir`, `mcopy`, content compared with the host sources), `tools/r11m-fatwalk.py --strict --vfat` (decodes
  directories, long-name chains, checksums, FAT copies), `scripts/r11k-assert.py` for the earlier rounds' sequences, `scripts/r11m-demo-judge.py` and
  `scripts/r11m-matrix-judge.py` for this milestone's transcripts.
* Claims are classified: **host build** (compiled / unit-tested on the host), **guest executed** (ran in the emulated machine), **independent comparison** (a host tool read
  the guest's result), **not tested**, **blocked**.

## 4. The integrated demonstration (`scripts/r11m-demo.sh`)

One scripted session per emulator on the paging kernels, then a second boot on the resulting image. Sequence `tests/r11m/seq-demo-a.txt` (QEMU; Tiny386 and i386VM variants
differ only in how the focus is switched and read back):

1. `PWD`, `DIR`, `MD SRC`, `CD SRC`, `PWD`, `COPY ../LONG.TXT SUPERBASIC_INTERPRETER.C`, `COPY ../README.TXT "Release Notes.txt"`, `DIR` (shows `SUPERB~1.C  205  SUPERBASIC_INTERPRETER.C`
   and `RELEAS~1.TXT  4011  Release Notes.txt`), `TYPE "Release Notes.txt"`, `CD ..`.
2. `START COUNTER.AOU 600 25 /CON:1` and `START TICKER.AOU 600 25 /CON:2` — two paged programs linked at the standard origin; `PS` lists both as `(paged)` on consoles 1 and 2.
3. Focus switching: Alt+F2 (console 1: `COUNTER 1 31`), Alt+F3 (console 2: `tick 32 of 600`), Alt+F2 again (`COUNTER 1 77`), Alt+F3 again (`tick 78 of 600`), Alt+F1 (shell prompt). The
   judge requires strictly increasing counters between the visits, no TICKER text on console 1, no COUNTER text on console 2, and no shell prompt on either (values are from
   one QEMU run; they differ per run).
4. `PS`, `KILL 65539`, `KILL 65540` (`job N killed`), `PS` (only the shell and the idle job; the killed jobs are listed as `(killed)` with their slots free).
5. `RUN PHOON.AOU "11 Jan 2024 11:57:00"` (x87, exit 0), `RUN CATFIL.AOU` (SDK utility), `RUN JOBT.AOU` (69 checks of the job table, baselines of address spaces, held bytes and heap after
   kills, at the same prompt), `PS`, `EXIT`.
6. **Reboot** the kernel on the final image: `DIR SRC` still shows both names; `TYPE "SRC/Release Notes.txt"`, `TYPE SRC/RELEAS~1.TXT`, `CD SRC`, `TYPE "release notes.TXT"` all show the file; `PS` is clean.
7. Host side: `fsck.fat -n`, fatwalk, and `mcopy` of both files compared byte-for-byte with `LONG.TXT` / `README.TXT`.

The QEMU run's screens are in `logs/r11m/demo-screens-qemu.txt` (one 80x25 snapshot per command). Result: `DEMO-ALL <emu> PASS` for QEMU (3 rounds, release gate), Tiny386 headless (2 counted rounds, legacy diagnostic) and i386VM (3 rounds, legacy diagnostic)
(`logs/r11m/SUMMARY.txt`). On i386VM there is no display: the focus is switched by ESC+digit in the input stream and the console text is read back with `CONDUMP`; on
Tiny386 the Alt+digit keys go through the terminal and `CONDUMP` shows the consoles; only QEMU shows the screens being switched.

## 6. Regression of the earlier rounds

`scripts/r11m-regress.sh` runs the R11K / R11H / R11F sequences **unchanged** on the R11M kernels (it was first written to run the frozen R11L kernels; here it runs
`build/r11m/...`): paging (MULTI, SAME/SAMELNCH, PGRUN, fault tests), MULTI/NEG, x87 and Phoon (PHCHK, FPMULT, PHDATE), the read-only block device, the non-paging default kernels, 3 rounds
on QEMU VGA (release gate) and 3 on each legacy diagnostic target (i386VM, Tiny386 headless; this regression was completed before the policy change), judged by `scripts/r11k-assert.py`: PASS 695, NA 15 (documented: TWICET W stdin, short PGRUN programs, QEMU 80-column cut), 43 failing checks all in the
22 groups that need R11K-only kernels or the host and are not part of this run (`tests/r11l/regress_filter.py`); **real failures 0**. NEG: 848 checks, 0 failures in each of the 12
transcripts. The frozen volumes are unchanged by the run (hashes before/after).

One regression was **found and fixed** by this re-run: a legacy `WIN1_` name longer than a full 8.3 name answered `FAT_ERR_NAME` (-46) instead of the R11E answer `CHAN_ERR_RANGE` (-14) because
`CHAN_NAME_MAX` had grown to 72 for native paths (`QDOSAPI` "overlong name is rejected" failed). `kernel/win1.c` now returns -14 for them, as before.

## 7. Clean-extraction smoke

The packaged archive is extracted into an empty directory and `scripts/r11m-smoke.sh` is run from there: it verifies `SHA256SUMS`, boots the packaged kernel on the packaged initial volume
on i386VM (demonstration phases A and B, judged, legacy diagnostic), and runs the VFAT sequences s4a/s4b after a reboot on QEMU VGA (the one bounded release smoke); Tiny386 is not part of the smoke. Result (`logs/r11m/smoke/smoke.log`): **SMOKE PASS** - SHA256SUMS verified (2556 files), i386VM demonstration PASS, `fsck.fat` clean, `r11m-fatwalk` 0 errors, mtools copy identical,
initial volume untouched, QEMU long name and alias listed after reboot, QEMU `fsck.fat` clean; Tiny386 **NOT RUN** in the smoke (`TINY386` unset). The smoke ran on the archive built from source
commit commit `26752eb`; the final archive differs from it only by this paragraph and the smoke log (source files identical).

| Defect | Cause | Fix / status |

| Tiny386-headless final image failed `fsck.fat` ("FAT copies differ in 1 entries": cluster 3168, FAT 1 = 0x0000, FAT 2 = 0xFFFF) after `JOBT` | most likely the emulator's unflushed stdio image writes lost when the harness kills it; not proven by guest tracing | **open, not fixed**; test-harness workaround only (`scripts/r11m-run-pc.sh`), not a durability guarantee; details and deferral in `docs/R11M-KNOWN-LIMITATIONS.md` section 5; images in `logs/r11m/noflush` |

## 9. Claim classification

* **Guest executed** (three emulators unless stated): all of sections 3 to 6.
* **Independent comparison**: file contents and long names read by mtools; `fsck.fat`; `r11m-fatwalk.py`; `r11k-assert.py` (the earlier rounds' independent oracles: host-computed Phoon dates etc. are part of those sequences).
* **Host build**: strict C89 `-Werror` compile of the common/runtime code in the configurations with and without each option; host unit tests (`logs/r11m/hosttests.log`: fatdir 124 ×5 shapes/options, vfat 343/24/73/9, vcon 104, blockrw 20, fat16w 290 ×3, BLOCK 88, LAYOUT 39).
* **Not tested**: real hardware; FAT32; non-ASCII names; Zork I (no story file was provided); the native GCC (not part of this milestone).
* **Blocked**: nothing in the plan.
