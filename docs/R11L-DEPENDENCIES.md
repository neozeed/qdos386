# R11L: what the historical tools need from QDOS/386

Machine-readable form: `docs/R11L-DEPENDENCIES.csv` (generated by `tools/r11l-deps-csv.py` from the real link inputs:
for each tool, every symbol its objects reference that an SDK library supplies, with the library and archive member).
**89 distinct symbols** (191 rows) in total; every one resolves inside the SDK (`libm.a`, `libc.a`, `libgcc-qd.a`, `libqdos.a`)
and the four links finish with no diagnostics (`scripts/r11l-link-tools.sh` fails on any linker output, because the
historical `ld` exits 0 after "multiple definition").

## Constraints that shaped the port

* **Memory.** A slot-1 program owns a 1 MiB window (0x240000-0x33FFFF) in which text, data, bss and the argument block live.
  The kernel heap (about 1.9 MiB) and the per-job stack (heap block, 64 KiB with `-DQDOS_APP_STACK=65536u`) are shared.
  Measured peaks are in `docs/R11L-SELFHOST-RUNTIME-REPORT.md`.
* **No `fork`/`exec`/pipes.** The driver `CC.AOU` starts each tool as a paged child (`qd_pg_startv`, R11K), waits with
  `qd_yield` on `qd_job_exit_status`, and passes data between stages through files on the FAT16 volume.
* **No directories.** Include search is `-I.`: the SDK headers are copied to the volume root under upper-case 8.3 names.
* **`struct stat`/`errno` layouts** come from `port/include` (the real definitions the tools were compiled against; an early
  build against a stale 20-byte `struct stat` crashed cccp - see `docs/R11L-TOOLCHAIN-PORT.md`).

## What is not needed

No `fork`, `exec`, `pipe`, `popen`, `system`, `alarm`, sockets, `mmap`, directory reading, wildcard expansion, `/tmp`,
or environment variables. The driver reproduces what `gcc`'s own driver does with those (run cccp, cc1, as, ld in order,
stop at the first failing stage, delete the stale outputs first).
