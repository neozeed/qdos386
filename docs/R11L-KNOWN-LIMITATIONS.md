# R11L: known limitations and the exact boundary of "self-hosting"

## What is claimed

*Guest executed:* inside QDOS/386 (i386VM harness, Tiny386 PC, QEMU PC - see the runtime report for which stage ran where)
the user types `HELLO.C` with the guest program `ENTER.AOU`, runs `CC.AOU`, which runs the historical **cccp (GCC 1.40),
cc1 (GCC 1.40), GNU as 1.38 and the binutils-1.94 i386 a.out `ld`** as guest programs, and then runs the resulting
`HELLO.AOU`. Every intermediate (`HELLO.I .S .O`, `CRT0.O`) and the final program are written to a writable FAT16 volume
by the guest. The host does not compile, assemble, link or transform `hello.c`.

*Independent comparison:* the host built the same program with the same historical tools (the "oracle", `scripts/r11l-oracle.sh`)
and the volume files are byte-compared to it with `mtools`/`cmp`, and checked with `fsck.fat` and `tools/r11l-fatcheck.py`.

## What is NOT claimed

* **The tools were not built inside the guest.** `AS/CCCP/CC1/LD.AOU` were produced on the host (bootstrap). The cc1 that
  compiled them is the same GCC 1.40, run on the host; the code generator tables come from the host bootstrap (`gen*`
  programs, bison 1.16). A guest that can rebuild its own GCC (compile cc1's 40 sources and link it) was **not tested**.
  Compiling a large tool source in the guest is covered only by the test corpus (MACROS, FUNCS, FPT, LSTDIO), not by the
  tools' own sources.
* The initial disk (kernel, shell, tools, SDK headers, CRT0.S, libraries `LIBC.A LIBM.A LIBGCC.A LIBQDOS.A`, `SLOT1.LD`) was
  populated by the host. `CRT0.O` is assembled in the guest from `CRT0.S`; the libraries are host-built (by GCC 1.40 and
  GAS on the host) and are not rebuilt in the guest. `ar` and `ranlib` do not exist in the guest.
* "Self-hosted GCC" in the sense of GCC compiling GCC on the target is therefore **not** claimed. The claim is: a guest-native
  C to executable pipeline made of the historical tools.

## Platform boundary

| Limitation | Consequence |
|---|---|
| Paging kernel required for `CC.AOU` | the driver is an unpaged slot-1 program that starts the tools as paged children (`qd_pg_startv`); a paged child cannot spawn. Non-paging kernels can still run each tool by hand from the shell (Stage 2/3 sequences). |
| Paging separates only image windows | heaps and stacks are shared; tools run **sequentially**, there is no isolation claim and no concurrent builds |
| Flat 8.3 root directory only | no `/`, `\`, `:` in names; SDK headers live in the root (`-I.`); `#include <sys/stat.h>` style paths are not available to guest-compiled programs (the SDK headers are flat) |
| Source files and outputs share the volume namespace | a program named like a tool or like a header overwrites it; `CC.AOU` refuses non-8.3 names (status 2) |
| Shell line 159 characters (`shell-l`), 15 user arguments, 432 bytes of argument strings | the linker command line is generated by the driver, not typed |
| 1 MiB program window | cc1 fits (463 K text + bss + 64 KiB stack in a separate heap block); a source whose compile needs more heap than the ~1.9 MiB kernel heap fails with an out-of-memory diagnostic from cc1 |
| FAT16 write path has no journal | write-through, ordered; a power cut can leave an orphan cluster chain or a lost directory entry (`R11L-FAT-WRITE-ABI.md`, 107 cuts tested) |
| libc | mixing fd-level and stream-level I/O on one file is unsupported; `tmpfile` returns NULL; `signal` handlers are never invoked; time is fixed |
| `ENTER.AOU` | a line consisting of a single `.` ends input and cannot be entered; no editing, no tabs from the console harness (typed sources are space-indented) |
| cc1 string pool | the guest cc1 merges identical string literals; the host-run oracle cc1 does not (assembly differs, behaviour identical) |
| Speed | measured wall times (host, emulator start to end of a sequence): i386VM runs the whole four-source end-to-end suite in about 5 s; Tiny386 in about 1.7 minutes for suites A+B (typed input paced at 20 ms per character, 2 s pause per console line); QEMU TCG in about 5 minutes (the VGA screen scrape through the monitor dominates). These are emulator speeds, not guest speeds: no claim is made about real hardware |
| Scripted input | Tiny386's terminal input drops scancodes of a burst longer than about 75 characters (a 99-character line lost its tail and its Enter). The harness therefore sends long lines one character at a time (`PC_KEY_DELAY`, default 0.02 s in `r11l-run-pc.sh`). An earlier "ld hangs on Tiny386" observation was this input loss (the shell was waiting for an Enter that never arrived), not a guest defect |
| QEMU transcripts | the judge reads 80x25 screen snapshots; a command's output that scrolls more than a screen is judged from its tail only (the `DIR` listing is checked on the final volume with `mdir` instead), and wrapped command rows are rejoined |

## Not in scope (unchanged from the plan)

Ring 3, FAT32/VFAT, partitioned boot, GRUB, virtual framebuffers, a graphical editor, demand paging, a Unix emulation layer,
a modern GCC, ELF.
