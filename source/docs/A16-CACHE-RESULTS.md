# Apollo 16 Phase 2B: results

All runs use fresh boots and the debug-port diagnostic output (`isa-debugcon` at 0x402). The VGA capture harness is not used.
Ticks are kernel timer ticks. Each reader prints one summary record, so concurrent readers cannot corrupt each other's output.

Notes:
- R18 large-set pass 2 is not in this serial matrix (the 200-second limit stopped those runs); the earlier VGA matrix
  measured it at 2,701 ticks on one CPU. The 2B pass 2 on one CPU is 1,146 ticks.
- Phase 2A's large-set errors (`FAT_ERR_IO`) reproduce here: 393 and 784 per run. Those are the same 8-entry configuration
  and retry-cap mechanism as the 8-reader defect, not device errors (see the design document).
- Cold streaming is slower with the cache than without it: a 1.5 MB sequential read is about 7x slower on one CPU and about
  15x slower on two. Every sector is a miss and an eviction in this pattern, and the synchronous fill and the reservation
  bookkeeping cost more than a direct read. This is a real cold-read regression, reported as measured.
- The foreground stays responsive: background progress during random reads is about twice the R18 rate, and far above
  Phase 2A's.

## Phase 2A large-set diagnosis

What was measured on the committed Phase 2A kernel (`R20GL`, serial matrix): every failed read returns `FAT_ERR_IO`, with
393 (pass 1) and 784 (cumulative, pass 2) failures per run, on one and two CPUs. No byte is wrong.

What the 2B diagnostic run established, on the same 8-entry cache and retry cap: a failure of this kind is a retry-limit
give-up, and give-ups equal reader I/O errors exactly, while device failures and cache waits are counted separately and
were zero. A restarted read re-probes from the start, and without reservations the sectors it had filled can be evicted
before it retries, so a long run of misses ends in the retry limit.

For Phase 2A itself the same mechanism is the most likely cause, but it is not confirmed. The diagnostic copy of the 2A
tree (with a per-job give-up counter) was built and not run, and the 2A serial runs do not print give-up counts. The 2A
tag and source are unchanged.

## Limitations

- The 8-entry cache is a stress configuration (about 4 KiB), not a production size. The defect it exposed is fixed by
  reservations; the default size does not reach the retry limit under this workload.
- 301 device failures produced 291 visible I/O errors in the 8-entry injected run. The missing 10 were superseded by a
  successful retry: their waiters could not take a reservation (the reader held its maximum of four), so the sector was
  evicted before the reader saw the error. This does not return bad data, but a device failure can be masked in that case.
- Injected failures are applied at the fill result. They do not model the controller's timing or a real timeout; the
  blkdebug path was not used.
- Cold streaming is slower with the cache (see Performance).
- Device identity is fixed at 0 (one IDE slave). Seeks and directory operations stay synchronous under the BKL. Writes
  are synchronous and only invalidate the cache; they are not restartable.
- Killing a process is tested through `QT_JOB_KILL` from another process. A process that is killed during its own
  synchronous trap is not separately tested.
- The eight-CPU result is one configuration (8 readers, default size).
- `R20_STAT_DUMP` and the test switches are diagnostics; they are not a public API.
